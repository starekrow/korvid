# core

The engine's floor: modules, the tick and its scheduler, entities and their components,
events, handles, memory, and the small libraries everything else is written with. Core
knows nothing about windows, files, graphics or games. A game doesn't call most of it
directly: it declares components, ktables, systems and handlers in a `ModuleDesc`, and core
stores them, schedules them, delivers events between them and accounts for their memory.

**Where a newcomer starts.** Writing a game touches these headers first, roughly in this
order. Each one's file comment explains its idea, with an example.

| header | for |
|---|---|
| `korvid/core/module.h` | `ModuleDesc`: declaring a module and its tables; startup and shutdown |
| `korvid/core/phase.h` | `SystemDesc`, `HandlerDesc`, and the `TickContext` a system works through |
| `korvid/core/component.h` | components: plain structs with a field table |
| `korvid/core/ktable.h` | ktables, where entities live: a fixed set of components, stored as columns |
| `korvid/core/event.h` | event types: facts one module tells others |
| `korvid/core/handle.h` | handles: how anything the engine hands out is named |
| `korvid/core/engine.h` | the `Engine`: publishing resources, pausing, quitting, lookups |
| `korvid/core/memory.h`, `arena.h` | which allocator for what; the scratch arena |
| `korvid/core/array.h`, `map.h` | the containers |
| `korvid/core/log.h`, `random.h`, `test.h` | logging, seeded randomness for the sim, a module's tests |

[Modules](../../docs/concepts/modules.md) puts the first five together in one worked
module, and [frame loops and scheduling](../../docs/guides/frame-loop-and-scheduling.md)
shows them running in a game.

Rules core enforces, stated once: no exceptions, no RTTI, no STL in the runtime; nothing
runs before `main`; every id is assigned at `engine_init` and cleared at shutdown; every
allocation has an owner; the same world produces the same state hash on any thread count.

## How it works

**Memory** (`memory.h`, `arena.h`, `pool.h`, `os_memory.h`). Allocation is ownership. The
general allocator is thread-safe and attributed: whichever module's code runs is charged
for what it allocates, so `mem_report` says where the bytes went. Arenas are linear and
reset at once; the calling thread's scratch arena is reset every frame (`MemScope` for
anything shorter). Pools hand out generational handles over slots on reserved pages, so
addresses are stable and a stale handle is caught. Heaps are budgets with soft and hard
limits that the root assigns to modules. [docs/design/allocators.md](../../docs/design/allocators.md) has the design.

**Handles** (`handle.h`, `kv_handle.h`). One 64-bit value: kind, generation, index. A
kind is an issuer registered with a resolve function, so anyone can turn a handle into a
pointer without knowing who made it, and tools can describe it. An issuer may also name
its handles (`name_of`, `find_name`): `handle_name(h)` is what a material, an asset or an
entity is called, and `handle_find(kind, name)` finds it again in a run that made things in
another order. Saves write named handles by name. [docs/design/handles.md](../../docs/design/handles.md).

**Modules** (`module.h`). Modules are the top-level structure of the code: everything
above core is one, and an executable is a list of them in dependency order, generated by
the build. A module owns the types the engine can see (its components, ktables and events,
declared once and known to everyone by name), places its systems in the tick's phases
with their reads and writes, and owns its state and memory. In code that is one
`constinit ModuleDesc` that `engine_init` reads once. [Modules](../../docs/concepts/modules.md) is the long version.

**The tick** (`tick.h`, `phase.h`, `engine.h`). `engine_frame(e, dt)` advances a fixed-step
clock and runs the ticks it owes, and none after a quit has been asked for. A tick is four phases (Input, PreSim, Sim, PostSim);
between phases the engine delivers events, runs handlers and applies commands; within a
phase, systems run in an order derived from their declared reads and writes, and the
independent ones run concurrently on the job pool. [Modules](../../docs/concepts/modules.md#how-code-flows-through-a-tick)
walks through it; [scheduling](../../docs/concepts/scheduling.md) has the ordering rules.

**Data** (`component.h`, `ktable.h`). A component is a plain struct with a field table,
which is the reflection everything reads: layout, hashing, comparison, describe, which
fields are handles. A ktable is a fixed set of components plus a capacity; the engine makes
it SoA columns on reserved pages, one handle kind, and resources `ktable` and
`ktable.Component` that systems name in their sets (`*.Component` means every ktable's).
Two forms narrow a wildcard or turn an edge around:
`*[Move2].Transform2` is that column in every ktable that also has `Move2` (and may match
none; `*[Parent+Collider2].Transform2`, in the ktables that have both), and a read marked `^` (`^.npc.Local2`) is of the phase's earlier value, so that
reader runs before the phase's writers of it instead of after: an AI reading where it
stands to write the intent a later system moves it by. Systems reach rows through the `TickContext`: `write_ktable`, `read<T>`, `write<T>`,
`view<A, const B>()`; in dev builds an access outside the declared sets asserts with the
system and resource named. Spawn directly when you hold the ktable's write; otherwise
`spawn_later` and `destroy` are commands applied at the phase boundary.

**Entity names** (`engine.h`). Any entity may have a name, unique among the living across
every ktable: `engine_entity_name_set(e, h, "old_man")` from code outside the schedule (or a
main-thread unit), `ctx.name_later(h, name)` and `ctx.spawn_named_later(ktable, name, ...)`
from a system, landing at the boundary in unit order. `engine_entity_find(e, "old_man")`
works from any thread at any time; a dead entity's name stops resolving with its handle.
A name is the entity's: hashed with its ktable, saved and restored with it (`save`), and
shown in the CLI as `@old_man` (`print @old_man/Transform2`) and under `/names`. Names are
for scripts, tools, saves and designers, a few lookups a tick behind a lock, not a
per-entity hot path. They are kept per ktable as sparse rows (`SparseRows`: by slot, each
with its entity's generation), which is also where attachments and property bags live.

**Attachments and property bags** (`ktable.h`, `phase.h`). A ktable is a fixed set of
components, and that is what makes iteration a walk over columns. Data that belongs to
one entity of many goes beside the columns, per entity:

- A ktable may list `attachable = "Talk, Quest"`. An entity of it may then carry one of each,
  stored sparsely by slot (`SparseRows`), reached as `ctx.attached<const Talk>(h)`,
  `ctx.attach(h, Talk{...})`, `ctx.detach<Talk>(h)` and
  `for (Attached<Talk> a : ctx.attached_all<Talk>(".npc"))` under the resource
  `ktable.@Talk` (or `*.@Talk`) in a system's sets.
- A ktable may declare `props = true`: each entity then has a bag of named ints, floats,
  bools, strings (interned) and handles, `ctx.prop_set_int(h, "gold", 3)`,
  `ctx.prop_str(h, "dialogue")` and the rest, under `ktable.@props`.

Both are the entity's: hashed with its ktable, saved and restored with its row (`save`),
described in the CLI, gone when it dies (stale at once, swept at the boundary). **Engine
systems never see them**: views are built from columns, so a `Sprite` attached to a label
is data and draws nothing. A ktable may not attach what it has as a column. Attachments
are slower to walk than a column and bags slower again: use them for what one entity of
many has (a quest, a chest's loot, what a designer typed on a map object), and ktables
for what every entity has.

**Events** (`event.h`, `timer.h`). Every type is a stream in the schedule: emitting is an
append into the running unit's writer (declared in `emits`), consuming is a declared read
that runs after the emitters in its phase and gets every event since its last run, in
unit order. Handlers are systems on one type with a phase; a type may ask for next-tick
delivery. An event with a schema whose handle no longer resolves is dropped from a batch
and counted. Scheduled events wait in a timer wheel keyed by tick; state triggers watch a
component field across ticks and emit `StateEdge`.

**Jobs** (`job.h`, `phase.h`). One pool of workers fed from one FIFO of chunks. `jobs_run`
cuts a range into chunks and the caller works the queue too, so nested batches progress.
`parallel_for` and `parallel_reduce` give each chunk its own event writer and command
buffer, merged in chunk order, so results never depend on which thread ran what.

**Cycles** (`engine.h`, `phase.h`). Beside the tick, two cycles a loop runs when it
wants: `Phase::Frame` once before each frame drawn (`engine_frame_cycle`), and
`Phase::Work` over and over while a unit says `ctx.more()` and the budget lasts
(`engine_work`; a unit sizes its slice by `ctx.time_left()`, its even share of what the
cycle has left). The frame loop gives Work its
slack, background work such as the platform's idle reads is a Work unit, and nothing in
either cycle is in a replay, so neither writes the simulation: a declared write to a sim
ktable fails init, and a spawn, destroy or timer into one is refused. [Cycles](../../docs/concepts/cycles.md).

**Tools in core.** The profiler (`profile.h`): zones, waits, marks and counters into
per-thread rings, read between frames into summaries, a frame tree, and a Chrome trace.
Names (`name.h`): interned strings compared as integers. Hashing (`hash.h`): one fixed
64-bit hash, never seeded. UTF-8 (`utf8.h`), the engine's one text encoding: total
decoding (malformed bytes are U+FFFD, one at a time), encoding, validation and copies
that truncate at a character boundary. A JSON reader (`json.h`) whose nodes and errors
carry their line, and KBOR (`kbor.h`), the binary form of the same tree, with JSON text
written back from either, glob matching for paths (`glob.h`: `*`, `?`, classes, `**`), SHA-256 for
content identity (`sha256.h`, apart from the table hash), the CLI registry (`cli.h`), a
seeded PCG32 and a Mersenne Twister that draws Python's and std::mt19937's numbers
(`random.h`), a test harness (`test.h`), a leveled log (`log.h`), and
formatted text and the standard streams (`format.h`: `format`, which is snprintf, and
`print`, `print_err`) without including `<stdio.h>`, which only core's own stream code
does. Files are the platform module's (`io.h`), queued or blocking.

## Using it

**Write a module.** A header declaring the record, a source defining it with its tables,
a `module.lua` naming the deps. [Modules](../../docs/concepts/modules.md) has the whole shape with a component, a
ktable, a system, a handler, timers, triggers and parallel work, and what happens to each
when the tick runs.

**Memory in a game**: the module arena for what lives as long as the module
(`arena_push<T>(self.arena)`), `self.general` for anything growable (an `Array` with
`alloc` set, a `Map` after `init(&self.general)`), `mem_scratch()` with a `MemScope` for
temporaries inside a call, and ktables for entities, which the game never allocates.

**Data from a file**: parse JSON (or KBOR) into the scratch arena, read what you know with
defaults, copy out what you keep:

```cpp
MemScope scope;
JsonDoc doc;
if (!json_parse(text, len, mem_scratch(), doc)) {
    KV_ERROR("mygame", "%s: %s at line %u", path, doc.error, doc.error_line);
    return false;
}
f32 speed = (f32)json_number(json_get(doc, doc.root(), "speed"), 120.0);
```

**Strings that are compared often** (event names, ids from a file) are interned once with
`name_intern` and compared as `Name`s from then on.

**Driving the engine yourself** (a tool, a test): `engine_init(e, modules, config)`,
`engine_frame(e, dt)` per frame, `engine_shutdown(e)`, then `names_shutdown()` and
`mem_shutdown()` last. `e.hash_ticks` logs the state hash after every tick;
`engine_hash_state(e)` returns it.

## Behaviour worth knowing

- **Ids are per engine.** `ComponentType<T>::id`, `EventType<E>::id`, ktable ids and
  resource ids are filled at `engine_init` and cleared at shutdown. Cache them in a
  `static const u32` looked up through the context, never across engines.
- **List order is the tie-break.** Modules start in list order and stop in reverse;
  systems with no edge between them keep module order then declaration order. Changing
  the list changes nothing a correct game depends on, and the schedule log says why
  each edge exists.
- **Access is checked in dev.** `ctx.write<T>` on a column the system did not declare
  asserts with the system and the resource named. A `cosmetic` component read by a sim
  system is rejected at init. Ship builds check nothing and trust the sets.
- **Determinism is by construction.** Chunks merge in chunk order, ktables iterate in slot
  order, events deliver in writer order, timers fire in ticket order. `--threads 1` and
  `--threads 16` hash the same. The hash covers sim columns only.
- **Scratch is frame lifetime on main, job lifetime on workers.** A pointer into scratch
  kept across a frame is a bug the poison fill finds in dev.
- **Pools and arenas have one owner thread**, asserted in debug. The general allocator
  is the only shared one; a worker's bare `mem_alloc` is attributed to the module whose
  system is running.
- **Handles in events are checked per batch**, not at emit: an event naming an entity
  destroyed since is dropped from that consumer's batch and `dropped_stale` counts it. In
  the emitting phase nothing has died yet (destroys are commands).
- **Order is per event type.** Every consumer sees one type's events in the same order,
  but two types are two streams: a handler on `Started` and one on `Stopped` cannot tell
  which came first. When that order matters, make the two facts one type with a field
  that says which, or keep the state in a resource and treat the events as "something
  changed". `event.h` says so at the top.
- **No waves.** A chain of events runs out in data order inside a phase; a loop reads
  early and goes round once a phase. Nothing is capped or carried.
- **Heaps fail, never kill.** An allocation past a hard limit returns null with the heap,
  module and category logged once; a spawn into a full ktable returns a null handle.
- **The profiler is on when something reads it** and compiles to nothing in ship.

## Not in this module

Windows, input, files and sockets ([platform](../platform/README.md),
[platform_hid](../platform_hid/README.md)); rendering ([render](../render/README.md) and
its backends); anything that knows what an entity looks like
([sprite](../sprite/README.md), [collision](../collision/README.md)); the frame loop and
options ([frameloop](../frameloop/README.md)); the CLI's transports (`cli`). Rewind, the
C ABI, runtime module loading, compound and script triggers, and simulation LOD tiers
are designed for and not built. Recording and replaying input is
[frameloop](../frameloop/README.md)'s.
